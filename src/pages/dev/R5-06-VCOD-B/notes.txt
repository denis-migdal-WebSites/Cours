- agile :
    - backlog : liste de features à implémenté priorisée
    - itération incrémentale :
        - timeboxed : 1 semaine à 1 mois
            - taille fixe (sauf e.g. due jours fériés).
        - au début : choix des features à implémenter
            -> de la conception à l'intégration, en passant par les tests
        - à la fin : démonstration auprès des clients => collecte le feedback et adapte les plans en conséquence.
            => s'assure demande = ce qu'ils voulaient.
            => coût modif moindre (car tôt)
                => flexible = agile :)
        => produit utilisable (ship) à la fin de chaque itération.
            => important car on est tj en retard
                => garantie d'avoir une version (récente) qui marche.
        => fast result.
        => tester des choses/tester des pistes. On se plante => converger vers un truc bien par itérations successives (d'où le real life feedback)
            => qu'est-ce qui marche/marche pas ?
        => évite le rush de fin de projet (plus beaucoup de tps pour tout finir)
    => approprié quand on navigue à vue : idée vague de ce qu'on veut.

#17 structure de scrum (process)
- product backlog
    -> hiérarchie de backlog possible (e.g. par (sous-)produit/par équipe/par components)
    - items : features / changes / defect / technical / technical debts (rendre visible / elles ont un coût financier -retarde le dev- #157)
    - features
        -> feature -> user stories
            -> pour qui, quoi, pourquoi
            -> discussion
            -> ATTD : condition de validation (acceptance)
        - estimer coût/complexité/etc.
            -> value/importance client.
            -> nombre (difficile) vs label (relatif gp).
                -> relative size + facile
                -> nombre forcément faux variance.
                -> mais moyenne quand nombre important "se compense".
                -> estimé par les devs
                    -> besoin mécanisme de consensus
                        -> e.g. planning poker.
                        -> au autre.
                        => pas débattre 2h.
                + pas un engagement (sinon inflation du coût pour "marge")
                -> pas besoin d'être précis => variance.
        - prioriser
        - refine = grosse feature en sous features + précises.
        - delete (archiver)
- sprint planning
    - établir le sprint goal pour le sprint qui arrive.
        -> pas y passer trop de temps => chef pratique.
    - casse features en tâche à accomplir
        -> sprint backlog
    - associe une durée à chaque tâche
        -> permet de voir la charge des personnes responsables
        -> pas passer trop de temps à estimer, et estimation toujours arbitraire/fausse.
    - ne peut changer une fois le sprint débuté.
- sprint execution : bosse en autonomie.
    - daily scrum/daily stand in : timeboxed 15min.
        -> lourd (surtout quand sous pression).
            -> chacun à son tour :
            (ce que j'ai fait, ce que je vais faire, obstacle).
        -> pause(s) café(s) = mieux.
- sprint review : présentation de ce qui a été fait auprès du client/users
    -> collecte des feedbacks et adaptations.
    -> démonstration plus que présentation (slides).
    -> peut faire plusieurs projets à la fois (l'un après l'autre ofc).
        -> un peu comme réunion de département / réunion de stakeholders.
- sprint retrospective (démarche qualité)
    -> retour sur le process. 
    -> lourd, surtout si sprint = 1 semaine.
    => mieux vaut une réunion d'équipe 1/mois ou des réunions ad hoc si difficultés.
    => ou fusionner avec le sprint planning, sans prendre 10 ans.
    => avoir un focus pré-déterminé sur des problèmes constatés :
        => e.g. améliorer les tests unitaires, etc.
        => pas une collecte de retours donc.
            => collecte de data objectives avant réunion.

=> on garde de la conception au tout début, mais sans trop prédire.
